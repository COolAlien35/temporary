# QuantumLoop API contract, revision 1

This contract guides B04–B20. **Existing** routes are implemented today; **planned** routes are schemas for later modules, not claims that those routes work. `frontend/lib/services/contracts.ts` and OpenAPI must converge on these shapes during B20. No browser-provided learner ID, role, score, simulated result, or answer key is authoritative.

## Common wire rules

- Base path: `/api/v1`. Breaking wire changes use `/api/v2`; additive optional fields and new routes stay on v1. Clients ignore unknown response fields. Removing a field or changing its meaning requires a new version. Routes return JSON except `204` and artifact downloads.
- Authentication: `Authorization: Bearer <Supabase access token>`. The server maps the verified subject to a local profile. Collection requests scope to that actor's authorized records. A route parameter may identify a resource or an instructor-scoped learner; it never grants access by itself.
- Identifiers: server-created domain records use canonical lowercase UUID strings. Existing curriculum IDs, algorithm slugs, challenge IDs, gate IDs, and provider device QRNs remain stable opaque strings; do not parse their spelling for authorization or semantics. Revision numbers are positive integers scoped to one resource. References to an absent, inaccessible, or deleted private resource return `404` unless a route explicitly requires `403` for an already disclosed membership.
- Time: wire timestamps are ISO 8601 strings with an explicit UTC offset (`Z` or `+00:00`); database timestamps are timezone-aware UTC. `due_at`, `expires_at`, `created_at`, and `updated_at` are instants. The profile's `timezone` is an IANA zone name (initial default `UTC`); streak/day and calendar displays use that zone. Date-only values use `YYYY-MM-DD` and state whose zone defines the day. No API accepts browser-local epoch milliseconds as an authoritative instant.
- Lists: new collection endpoints accept `limit` (default 25, maximum 100) and an opaque `cursor`; respond `{ "items": [...], "next_cursor": string | null }`. Sort by a documented field plus UUID tie breaker; cursor encodes both and is scoped to the same filters/actor. Invalid/expired cursors return `400 invalid_cursor`. Current **existing** `/cohorts` and `/cohorts/{id}/members` remain array responses with `limit`/`offset` (default 50, maximum 100) until a versioned migration; do not silently reinterpret them as cursor endpoints.
- Request body size and field limits are enforced per route. Unknown write fields are rejected. Numeric probabilities are finite JSON numbers in `[0,1]`; vectors declare their ordered basis labels and comparison basis. Arrays, circuit depth, shots, artifact size, and text lengths receive explicit caps with their implementing module.
- Errors currently use `{ "error": { "code": string, "message": string, "requestId": string } }` plus `X-Request-ID`. New routes retain that envelope and may add `details` with field names and safe machine-readable reasons. Never expose hidden keys, tokens, stack traces, provider secrets, or another learner's data. `requestId` identifies one HTTP request; logs and job records carry it for tracing.

## Write, version, and retry rules

- New create/submission operations that can charge a provider, create an attempt/job, publish, enroll, award, or post a message require `Idempotency-Key` (client-generated UUID, 36 characters) and retain committed outcomes for at least 48 hours. The key scope is authenticated actor + method + route template + key. Persist a hash of the validated request body and resulting resource ID atomically with the domain write. Repeat key and same body returns the same logical outcome/resource; repeat key with a different body returns `409 idempotency_conflict`. A transient failure before commit is retryable with the same key; an uncertain external submission enters reconciliation. Domain uniqueness remains the longer-lived defense after key retention expires. Do not cache raw bearer tokens or invitation secrets in the idempotency record. A retried invitation create returns its existing invitation ID without reissuing the one-time token.
- Editable resources return an integer `revision` and `ETag: "rev-<revision>"`. Update/delete requests require `If-Match` with the last observed ETag; missing precondition returns `428 precondition_required`, stale revision returns `412 revision_conflict` with the current revision only if the actor may read it. Revision and mutation change atomically. Immutable published versions, run snapshots, prediction locks, and assessment attempts receive new IDs instead of in-place edits.
- An accepted background operation returns `202`, `{ "job_id", "status": "queued", "status_url", "resource_id"? }`, `Location: <status_url>`, and `Retry-After` in seconds. Polling returns an authorized job with status `queued | running | succeeded | failed | cancelled | timed_out | unknown`, timestamps, safe error, and result link or embedded bounded result on success. Cancellation is idempotent; a terminal success cannot be rewritten to cancelled. A remote-provider timeout after submission may become `unknown` until reconciliation, never an automatic duplicate charge.
- `GET` and status polling may retry on network failure, `429`, or `503` with bounded exponential backoff and jitter, respecting `Retry-After`. A mutating request retries only with the same idempotency key and unchanged body. `401` triggers one provider session refresh before retry; `403`, validation `4xx`, and `412` require user action or conflict resolution. Clients do not retry `409 idempotency_conflict` with a new key automatically.
- Realtime events are hints: `{ "event_id": UUID, "type": string, "resource_id": UUID, "revision": integer, "occurred_at": UTC timestamp }` plus typed payload. Reconnect loads the authorized snapshot/events after the last revision. A missed event never substitutes for durable state or polling.

## Shared schema vocabulary

`UUID`, `UTC`, `Slug`, and `QRN` follow the rules above. `Page<T>` is the list envelope. `Actor` is derived from the bearer token and database; it is absent from client write bodies. `ArtifactRef` is `{id: UUID, kind: string, checksum_sha256: 64-character hex, bytes: integer, download_url?: string, expires_at?: UTC}`; URLs are short-lived and issued only after ownership checks. `JobRef` is the `202` shape above. `Job` adds status, `created_at`, `started_at?`, `finished_at?`, `error?`, and `result?`.

The current B06 `CircuitDraft` is `{name,qubits,gates}` and its stored `CircuitSnapshot` adds `schema_version:1`. A `Gate` is `{id,type,step,qubit,target?,control2?,theta?}`. The current persistence API supports 1–8 qubits, at most 256 gates, steps 0–511, and a 32,768-byte draft. `CircuitRead` is `{id,revision,snapshot,checksum_sha256,created_at,updated_at}`. The checksum identifies the canonical snapshot; revision and checksum are returned outside it. Current local Aer results follow the declared `measurement_qubits` order, with bitstrings read left to right in that order; absent explicit measurements default to all qubits in descending index order. Angles use radians. The local `AerResult` shape is `{backend:"qiskit_aer",sdk_version,aer_version,shots,seed?,measurement_qubits,basis_labels,exact_probabilities,counts,capabilities,statevector?:[number,number][]}`. Frequencies are derivable from counts and shots. Statevectors are omitted above five qubits. Current limits are 8 qubits, 8,192 shots, and 64 MB simulator memory. The shared multi-provider `Result` vocabulary remains `{backend: string, circuit_revision: integer, shots?: integer, seed?: integer, counts?: Record<bitstring,integer>, exact_probabilities?: Record<bitstring,number>, sampled_frequencies?: Record<bitstring,number>, statevector?: ArtifactRef, capabilities: string[], sdk_version?: string}`. Providers must declare measurement, noise, and result capabilities before sharing this contract.

`AssessmentAttempt` is `{id: UUID, kind: "unit-quiz" | "circuit-challenge" | "lab-challenge" | "code-challenge" | "assignment", content_id: string, content_version: integer, status: "pending" | "graded" | "failed", submitted_at: UTC, score?: number, passed?: boolean, feedback: string[], job_id?: UUID}`. Learner responses and immutable circuit/code snapshots are returned only to authorized learner/instructor views. Client-provided scores and outcome vectors are ignored. `QuizQuestionPublic` contains ID, prompt, choices, concept IDs, and allowed attempt metadata; it excludes answer keys and unreleased explanations.

`PredictionSubmission` is `{schema_version:1,lesson_id,lesson_version,learning_session_id,prediction_vector,basis_labels,measurement_qubits,comparison_basis,confidence?}`. Vectors contain probabilities in `[0,1]`, sum to 1 within `1e-6`, and cover every measured bitstring exactly once. `measurement_qubits` maps each bitstring position from left to right to a circuit qubit; the current contract limits it to eight unique indexes from 0 to 7. `confidence` is separately reported in `[0,1]`. The current lab's percentage sliders must be divided by 100 before submission. The persisted session binds to the separate curriculum `content_version`, which must advance whenever learner-visible content changes.

`PredictionPair` is `{schema_version:1,prediction_id,run_id,prediction_vector,simulated_vector,basis_labels,measurement_qubits,comparison_basis,metric_version:"tvd-v1",prediction_match,backend,shots?,seed?,circuit_revision}`. `prediction_match = 1 - 0.5 × Σ|prediction_i - simulated_i|`, without persistence or display rounding. The pair is constructed from the persisted successful run in prediction label order. A pending, failed, cancelled, or unknown run has no simulated vector or agreement score. Every prediction can contribute at most one bound run; unpaired practice runs do not contribute to prediction agreement. B05.P still needs bounded tutor history and connected UI work.

## Implementation gates

Current cohort routes predate the complete write/paging conventions. B04/B20 must migrate them deliberately and test old clients or introduce new endpoints; this document does not retroactively make them conform. B05.P, B07, B08, B09, B10, B13, B16, and B19 own their detailed validation schemas and capability limits. Contract tests must compare Pydantic OpenAPI and connected TypeScript shapes as each route is implemented. The B22 acceptance suite checks cross-account authorization, replay behavior, stale revisions, pagination, UTC/zone boundaries, and failure recovery.
